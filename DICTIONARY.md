# mathacademy_timeback — dictionary

The product-management lens on **Math Academy's data for Alpha's students, and the Timeback record beside it**. Two halves, in this order: **this skill's store** holds Math Academy's own record (course, progress, XP remaining, grade, completion; every task since 2025-07-01 with its three clocks and Math Academy's course attribution; nightly history; knowledge maps), the truth about what a student did and how; **Timeback** holds who sits where (rosters, seats, sections, flags, grades) and the Timeback course each event was filed under. The store's sections come first below; the Timeback containers follow, because the roster half and the filed-course half still live there. Every task a student completes on Math Academy reaches Timeback as a Caliper event and is stored in Timeback's own systems: OneRoster (results, line items, enrollments, classes, courses, users) and EduBridge analytics (per-event facts and daily rollups). This skill reads those, plus one container of its own: a **store of Math Academy's own records**, refreshed nightly from the Math Academy API and matched to Timeback students (true course, exact XP remaining, grade, SAT estimate, per-task engaged and productive time, course history, and the knowledge map on demand), served behind the reader's Timeback token. Readers never call Math Academy, and need only a Timeback credential.

Timeback **self-describes its structure** at `GET https://api.alpha-1edtech.ai/openapi.yaml` (OneRoster and gradebook routes, OpenAPI 3.1) and `GET https://api.alpha-1edtech.ai/edubridge/openapi.yaml` (EduBridge analytics, OpenAPI 3.1). Both are public. That is the table of contents; read it fresh. This file does not restate the schema. It adds the meaning the schema cannot carry: how each field is born, what its values mean, how the pieces connect, and the traps.

Math Academy is the core mathematics app for Alpha students in grades 4 to 12. A student is enrolled in one Math Academy course at a time (grade-level courses, Prealgebra, Algebra I, Geometry, Algebra II, Precalculus, Integrated Math, SAT courses, AP Calculus). Math Academy runs the student through lessons, reviews, quizzes, multistep problems, placements, exams and occasional supplemental tasks, awards XP per task, and reports each completed task to Timeback as one Caliper event. This dictionary is for a reader who wants to know what a Math Academy student did, how they are doing in their course, and whether Timeback's record of them is coherent, without touching Math Academy itself.

## The native surface (how the reader reaches the data)

- **Base:** `https://api.alpha-1edtech.ai`. **Auth:** OAuth 2.0 client-credentials exchange. **The token mint is the one POST a read-only reader makes**: POST `grant_type=client_credentials` with the client id and secret (HTTP Basic or form fields) to `https://prod-beyond-timeback-api-2-idp.auth.us-east-1.amazoncognito.com/oauth2/token`; the response is `{access_token, expires_in, token_type}` (no `scope` field is returned, so a scope problem shows up only as a 403 on the first call). Send the token as `Authorization: Bearer <token>` on every call, cache it for its lifetime (one hour as served), and mint again on a 401. The two OpenAPI files above are keyless.
- **What key:** a Timeback API client with **read-only** scopes for OneRoster rostering and gradebook and for EduBridge analytics (the scopes `powerpath.readonly` and `analytics/v1p0/readOnly` were sufficient for every call in this skill). One client per person or agent, never shared, requested from the Timeback platform team; this skill issues none. A 403, or an empty result on a route that returns rows for a colleague's key, is a limit of your key or its org, not an absence of data.
- **Self-description:** the two OpenAPI files. Field inventories, enums, filter grammar and response shapes live there. Filter grammar this dictionary relies on: `filter=<field><op><value>` with `=`, `~` (contains), `>=`, `<=`, joined with ` AND `; dotted paths reach nested references (`student.sourcedId`, `class.sourcedId`, `course.sourcedId`, `metadata.appName`). Quote values with single quotes and URL-encode the whole filter (spaces, quotes, `~`, `>=`). The proprietary `search=` parameter is honoured on `courses/` and ignored on `classes/` (trap 14).
- **Wire shape** (verified, probed 2026-09-16 and 2026-09-17): list routes return `{ "<collection>": [ ... ], "totalCount", "pageCount", "pageNumber", "offset", "limit" }` with `limit` capped at 3000. Instance routes return `{ "<singular>": { ... } }`. References inside rows are `{ "sourcedId", "href", "type" }` blocks, and on enrollment rows they also carry a display `name`. EduBridge daily and enrollment routes return one JSON object keyed by date, then subject, then (in `factsByApp`) app; the weekly facts route returns an object `{ message, startDate, endDate, facts: [ …event rows… ] }` covering every app the student used that week (thousands of rows a week for an active student; there is no server-side app filter, so keep `app == "Math Academy"` yourself).
- **Transient failures:** a small share of calls in a long run come back as connection resets or 5xx; retry once after a short pause. 429 has not been observed on these routes.
- **Scope:** a Timeback service credential reads all students in its organisation tree. Reads outside it return empty, not 403. See § The range of an absence.
- **Containers, and which fields each one carries** (this list is the RANGE of every absence claim in this document):

| Container | Native route | Carries for Math Academy |

The completion percent lives in three containers (results, enrollments, and the store's `progress`); XP per task lives in two (results and weekly facts); lesson titles live in two (line items and weekly facts). An absence claim about any of those must name which container was read. The task type lives only inside the task URL, which appears on both results and line items. **Retention horizon:** none is published. The oldest reachable Math Academy result is found with `GET .../assessmentResults?filter=metadata.appName='Math Academy'&sort=scoreDate&orderBy=asc&limit=1`; anything older is undecidable here, not absent.

### The range of an absence

Three different things can make a read come back empty, and only one of them means "the student did nothing":

- **Key range.** Your credential does not cover the student's org. Tell: the same call for a student you know is covered returns rows.
- **Container range.** You read the wrong container, or bounded it wrongly. "No Math Academy result in the last 14 days" is a claim about the results container, filtered by `metadata.appName='Math Academy'`, for that student, in that window, and nothing more. It says nothing about enrollments, about other apps, or about days before the window.
- **Time range.** Nothing older than the oldest reachable result is decidable.
- **A fourth case, not an absence at all: the events went somewhere else.** Math Academy's own record (this skill's store) can show real progress, or a completed course, for a student who has **no Math Academy result in Timeback ever** under this key. Their events reached Timeback under another identity, or never arrived (a broken Caliper link or a duplicate account). Tell: store row matched and `progress > 0` or `completed` set, results container empty for the `user.sourcedId`. Report it as a platform finding (open question, ticket 23), never as "never active".

So "quiet" in this skill means exactly: no Math Academy task for that student in that window in the store's day rows (Math Academy's own record for roster students, ENABLEMENT A4), or, when you read Timeback instead, no Math Academy result in the results container under a key known to cover them. Name which; the two coincide except for the handful of tasks Timeback never received (store trap (f)). Check the store row before calling a quiet student inactive.

## Genesis vocabulary

Every field below names its genesis in the contract's closed set: **captured** (from what?), **computed** (how? as of what?), **copied** (from where?), **judged** (by whom? when?), or **truly unknown**. Hybrids compose the lineage. Nearly everything Math Academy here is **copied**: Math Academy captured it, the Caliper event carried it, and Timeback stored it. A copied value is Math Academy's claim, stored by Timeback, and this dictionary says so rather than presenting it as Timeback's own measurement.

## The load-bearing rules

- **Math Academy's own record is the truth about the student's work; Timeback's record is the truth about the seat.** `[owner, 2026-09-18]`. Where the two disagree (course, progress, a day's tasks), report both and route the disagreement; never overwrite one with the other. The store serves Math Academy's half without a Math Academy call by the reader.
- **Every Math Academy task is one Caliper event, and the event is the unit of everything Timeback holds about the work.** `[platform-note]`, verified by probe. Timeback stores it as one assessmentResult whose `sourcedId` is `caliper_` plus the Caliper event id, one assessmentLineItem, one EduBridge ActivityEvent row and, for most tasks, one TimeSpentEvent row. Nothing arrives per question, per minute, or per login.
- **The course an event is filed under is the Timeback enrollment the platform matched at ingestion, never the course Math Academy says the student is in, and not necessarily the student's current enrollment.** `[platform-note]`, verified by probe and by every cold run. The filed course is what the event's line item carries (`assessmentLineItem.course.sourcedId`). Events are routinely filed under an enrollment since marked `tobedeleted`, a student can have events with no current Math Academy enrollment at all, and **events can be filed under a course the student has never held an enrollment in, in any status** (observed 2026-09-18: 154 results under Integrated Math I (Honors) for a student whose nine enrollment rows include no such course, and a 176-task Algebra II episode with no Algebra II seat ever). So "filed under" means the line item's course, which is usually but not always one of the student's seats; a Timeback-filed timeline (ENABLEMENT B9) must start from the line items, not from the seats. Two consequences: (a) if the enrollment is wrong, every event is filed under the wrong course and no field on the event says so (trap 10; the store's `courseAgreement` is the check, ENABLEMENT A7); (b) to know where an event was filed, read its line item, never the student's current enrollment (trap 21, ENABLEMENT B7). Measure: for one UTC day of Math Academy results, count rows whose line item course differs from the student's current in-window Math Academy enrollment course, and rows whose student has no such enrollment.
- **Timeback's progression engine acts on a Math Academy event only when the course completion percent reaches 100 and the course is on an approved list of Timeback course ids.** `[platform-note]` only; no wire probe can confirm it. TimeSpentEvents are skipped by progression. Every other event is stored and never acted on. The approved list is not served anywhere the reader can reach (open question #7).
- **Math Academy is grade 4 to 12 only** `[platform-note]`; a student below grade 4 in a Math Academy class is a roster fact to question, not a Math Academy fact.
- **No real student belongs in the bare `Math Academy` course or the `Beyond AI` courses** `[owner, 2026-09-17]`. Those courses carry no XP size. A non-test student found there is a roster defect to report (trap 12).

# The native map (the census)

### The Math Academy snapshot store — this skill's one container that is not Timeback's

- **What it is:** a copy of Math Academy's own student records, pulled from the Math Academy public API (`beta10`) and matched to Timeback students, so that readers get the figures Timeback never receives without calling Math Academy themselves. **Refreshed nightly** (owner's approval and the AlphaInsights lead's yes, 2026-09-17): at 03:00 America/Chicago a scheduled function reads the bulk students list (four pages), the Timeback roster, matches them (first by the Math Academy id already stored, then username, then one lookup per new student), and rewrites the store; at 03:45 a second run pulls Math Academy's per-task **activity analysis** (engaged and productive time) for every student who had a Math Academy result the previous local day. Every night's course figures are also appended to a per-student **history**, so course changes and completion dates accumulate from the store's first night. The **knowledge map** is fetched **on demand only**, one live call when a reader first asks for a student's map, cached for seven days. A student missing from the snapshot is looked up live once when first asked for. Every response carries `snapshotAt`; `stale` turns true when a night is missed.
- **Genesis:** `mathAcademy.*`, `history[]`, `tasks[]`, `knowledge` are **copied** (Math Academy computed them; the nightly or on-demand pull stored them). `matchedBy`, `courseAgreement`, `mathAcademyState` are **computed** by this skill. `timeback.currentMathAcademySeats` is **captured** live from Timeback at read time, with the reader's own token.
- **Where the key lives:** the Math Academy key is read at run time from one Secrets Manager secret by the two functions' roles; it is never on the wire, in a document, or in a reader's hands. Readers use only their Timeback token.
- **Native:** student routes `GET <front base>/store/student/{sourcedId}` (+ `/activity`, `/courses`, `/history`, `/knowledge`), cohort routes `GET <front base>/store/course/{course.sourcedId}` (+ `/students`, `/activity?date=`), `GET <front base>/store/finishers?since=` and `GET <front base>/store/courses`, all behind the reader's Timeback token except `/store` and `/store/courses`; `GET <front base>/store` (status: `snapshotAt`, `snapshotAgeHours`, `stale`, `schedule` {next due, whether the cron has ever fired, scheduled / manual / scheduler-test run counts}, `history[]` {at, source}, `activityLastDate`, `lastActivityRun`, `backfill`, `health`, `snapshotCalls`, `readCalls` {maLookupOnMiss, maKnowledge, maActivityBackfill (Math Academy calls), maActivityBackfillStudents, counterNote} open to anyone; `counts` and `byCourse` only when the request carries a Timeback token Timeback accepts, else `countsGated: true`). `GET <front base>/store/course/{course.sourcedId}` (counts) and `…/students?agreement=<value>` (rows) both need the reader's token. Only freshness, health, schedule and Math Academy's course-name map are served without one: aggregate counts about the school's students are not public. Per student, each with `Authorization: Bearer <the reader's Timeback token>`: `GET <front base>/store/student/{user.sourcedId}` (or `?email=`), `…/history` (one row per night), `…/activity?from=&to=` (Math Academy's per-task analysis), `…/knowledge[?courseId=&refresh=1]` (the map, cached 7 days). The route replays that token against Timeback (`GET users/{sourcedId}`, then `GET enrollments`) and serves the row only if Timeback answers 200 for that student under that token: **you can read from the store exactly the students your Timeback key can read.** A 401 or 403 is your key's limit. Three reads reach Math Academy, all counted under `readCalls`: a per-student read of a student missing from the store (one live lookup, once per 24 h; a nightly attempt counts), a knowledge-map read (one per student per course id per 7 days), and the first `/activity` read of a student never backfilled (about five calls, once). Every other read, including all later reads of those students, makes no Math Academy call.
- **Row shape:** `{ sourcedId, snapshotAt, rosterReadAt, snapshotAgeHours, staleAfterDays, stale, apiVersion, inSnapshot, matchedBy, matchConfidence, figuresAsOf (ISO timestamp), figuresBasis, isTestUser, unmatchedReason + lastTriedAt (unmatched rows only), mathAcademy {…} | null, minimalView, mathAcademyState, timeback { currentMathAcademySeats[], readAt, enrollmentsStatus }, courseAgreement, courseAgreementAtSnapshot, seatsAtSnapshot[], note }`. A seat, in `currentMathAcademySeats[]` and `seatsAtSnapshot[]`, is flat: `{ enrollmentSourcedId, courseSourcedId, courseName, classSourcedId, beginDate, endDate, pctCompleteApp }`. `?minimal=1` serves `mathAcademy` without `username`, `firstName`, `lastName`, `league` and `schedule`, for readers who need only the figures and the agreement. `mathAcademy` is copied as Math Academy serves it, artefacts included (`schedule.startDate` has been seen as the literal string `Invalid date` on a just-created account). `timeback.enrollmentsStatus` is the HTTP status Timeback gave for the live enrollments read under your token; anything but 200 means the live seats are unknown, not empty.
- **Freshness fields:** `snapshotAt` (when the Math Academy pull began), `rosterReadAt` (when the Timeback roster that decides who is `not in snapshot` was read), `snapshotAgeHours`, `staleAfterDays` (2 while the nightly runs: a missed night shows as `stale` the following day) and `stale`. `figuresAsOf` is the timestamp of the read that produced the Math Academy figures and `figuresBasis` says whether Math Academy answered a direct per-student call or the figures come from its bulk list, which can lag its live record by up to a day. `GET /store` also serves `history[]` (every snapshot ever loaded, each with `at` and `source` = `schedule`, `schedule-test` (a one-off proof of the scheduler on 2026-09-17) or `manual`), `schedule.firstScheduledRunHasHappened` and `schedule.nextSnapshotDueUtc`, so a reader can tell a store on its first day from one whose cron is broken without waiting for `stale`. The store began on 2026-09-17 with manual loads; the first 03:00 run is due 2026-09-18. A day can hold more than one snapshot, so `/store` and a row read minutes apart can carry different `snapshotAt` values; pin every figure to the one on its own response. `readCalls` is estate-wide, not per reader. Math Academy's own dates (`startDate`, `completed`, `createdLocal`) are local calendar dates or local timestamps and can post-date the snapshot that reports them. Past `staleAfterDays` a reader quotes Math Academy figures only with their date and takes progress from Timeback's newest result.
- **Cohort routes:** `GET <front base>/store/course/{course.sourcedId}` (token) returns the roster of that Timeback course at `rosterReadAt` counted by `courseAgreementAtSnapshot` (`nonTest.byMathAcademyState` counts each student's CURRENT Math Academy course; SAT Math Prep students count as "in progress" there although no state can be read on that course (progress null): read `completed` per row instead; which under a `disagree` row is another course: a `completed` there can be a Prealgebra finisher seated in Algebra I; students who finished THIS course and were re-seated by progression are not on its roster, so the finisher count comes from `/store/finishers` and `/history`, ENABLEMENT A5), with `testUsers`, `maNotStarted` and a `nonTest` block (`students`, `byAgreement`, `maNotStarted`, `byMathAcademyState`) that excludes test users (the top-level counts include them); every block includes the `no math academy record` bucket, so each sums to its `students`. Read `nonTest` first: a whole `disagree` bucket can be test accounts. The list route is the whole course at snapshot time; for one section intersect it with that section's enrollments. Its id fields are numbers where Math Academy's are (`mathAcademyCourseId`, `taskId`, `topicId`, `courseId` on activity and history rows); Timeback's `sourcedId`s are strings; `GET /store` carries the same for every course under `byCourse`. `…/students[?agreement=]` (token) lists the rows: `{ sourcedId, courseAgreementAtSnapshot, matchedBy, matchConfidence, isTestUser, isLikelyTest, classSourcedIds[], mathAcademyState, mathAcademyCourseId, mathAcademyCourseName, progress, xpRemaining, completed, startDate, estimatedScore, deactivated, figuresAsOf }` under `rows` with `count`, `nonTestCount` (rows with `isLikelyTest` false) and `students` (the same count as `count`, kept for older readers); `classSourcedIds` gives the section(s) so one section's roster is a filter, not 33 enrollment calls; an unknown `?agreement=` value is a 400 with the allowed list. `…/activity?date=YYYY-MM-DD` (token) returns the day totals of every roster student who has a store row and a pulled day, each row with `isLikelyTest`, plus `windowUtc`, `totals` (the rows without error summed), `studentsWithError`, `rosterStudents` (the whole roster, test users included), `rosterNonTest`, `studentsWithStoreRow` and `rosterWithoutMathAcademyRecord`: the denominator for "share of my class active" is `rosterNonTest`, not the rows. An unknown course id is a 404 on every course route; a malformed date is a 400; a day after `activityLastDate` (the current day, or one the nightly has not pulled) is served with `dayStatus` "partial: …" and whatever rows the backfill or on-demand reads have written, never as a complete day; a day that has not happened yet returns no rows and says so. `GET /store/courses` maps Math Academy's course ids to names. Per-student rows cost about a second each; the cohort routes answer in one.
- **`episodes[]`** (`…/courses`) — Math Academy's own attribution of every stored task to its course, grouped: `{ mathAcademyCourseId, mathAcademyCourseName, firstTaskAt, lastTaskAt, lastLessonAt, firstDayChicago, lastDayChicago, tasks, lessons, xpAwarded, byType }`, ordered by first task, with `currentCourse` and `coverage` beside them. **computed** by this skill over **copied** task rows. This is the course history independent of Timeback seats and of the Timeback course each event was filed under; an episode's `lastLessonAt` is the date Math Academy usually stamps `completed`. `GET <front base>/store/finishers?since=YYYY-MM-DD[&mathAcademyCourseId=]` lists every store row whose current Math Academy course carries `completed` on or after `since`, or sits at progress ≥ 0.995, or (for a student with no current seat) sits at progress 0.95 to 0.994 (`bucket`: `completed` | `at 100, not marked complete` | `left the roster near the end, not finished`; `byBucket`; rows carry `startDate`, `daysInCourse`, `offRosterSince`, `timebackCourseSourcedIds[]`; `count`, `nonTestCount`); a student Math Academy has already moved to a new course is not there (ENABLEMENT A5, union with B6 for a window that predates the store).
- **`history[]`** (`…/history`) — one row per **date** since the store began (2026-09-17; the last snapshot of a date wins, so `nights` counts dates while `/store` `history[]` counts every load): `date`, `courseId`, `courseName`, `progress`, `xpRemaining`, `completed`, `startDate`, `grade`, `letterGrade`, `estimatedScore`, `deactivated`, `state`, `agreement`, `tbCourseIds`. **copied** nightly. A course change is a different `courseId` between two dates; the last row of the old course carries its `completed` date **if Math Academy had set it before the student was moved** (Math Academy serves only the current course, so once moved, the old course's completion date is gone from the main row and survives only here). Nothing before the store's first date is knowable here (the store's `/courses` episodes hold Math Academy's half back to 2025-07-01 and Timeback's results the filed half: ENABLEMENT A9, B9). A date absent from the list is a night the refresh did not run, a night the student was not on the roster, or a night the student was on the roster but unmatched (`hist#` rows are written for matched roster students since 2026-09-17 and for off-roster students with a row since the load of 2026-09-19; an unmatched roster student has `nights: 0`, and a student who left the roster before 2026-09-19 has no rows for the nights before that). `progress` is absent on a row where Math Academy served null (SAT Math Prep), never coerced to 0.
- **`tasks[]` and `days[]`** (`…/activity`) — Math Academy's own per-task record for the days the store pulled: `type` (Math Academy's own vocabulary: `Lesson`, `Review`, `Quiz`, `Multistep`, `Placement`, `Exam`, `Supplemental`), `xp` (the task's **nominal** value) and `xpAwarded` (what the student got, signed; **this is the number Timeback copies as `metadata.xp`**, so join and sum on `xpAwarded`, never `xp`), `questions`/`questionsCorrect`, `startedEpochMs`/`completedEpochMs`, `courseId`/`courseName` and `topicId`/`topicName` (Math Academy's ids, the same numbers as in Timeback's task URLs), and the **three clocks**: `timeElapsedMs` (wall time on the task), `timeEngagedMs` (time Math Academy judged the student attentive; **this is the one Timeback receives, as `activeSeconds`**), `timeProductiveMs` (time that advanced the task; Timeback never sees it). **Every clock and epoch is milliseconds**, on tasks and on `days[]` alike. `days[]` is the store's own sum over the kept tasks: `{ date, numTasks, timeElapsedMs, timeEngagedMs, timeProductiveMs, xpAwarded, questions, questionsCorrect, windowUtc, error, fetchedAt }`; `error` is set instead of the figures when Math Academy refused that student's activity (`HTTP 404`/`401`, `gave up`) or when the student had no Math Academy id after the lookup (the text says so). **copied** (tasks) and **computed** (day sums). The response also carries `snapshotAt`, `stale`, `storeBegan`, `activityLastDate`, `dayBoundary`, `units`, `coverage`, `daysRequested[]` (a status per day when the range is 90 days or fewer; `pulled (today, partial: the day is not over)` marks the current day) and, when `days[]` is empty, `reasonIfEmpty`. What the two extra clocks mean is Math Academy's own analysis and its exact rules are **truly unknown**; the tells that held in cold runs: elapsed far above engaged = a task left open; engaged near elapsed but productive low = attentive but stuck (multistep problems run about a third productive); placements behave like lessons. **Day boundary:** the store defines a day as an America/Chicago day and keeps a task by its Math Academy completion time inside that window, asking Math Academy for two of its own days to cover it (Math Academy's date parameters run on its own clock, observed as UTC). Range: for a student the backfill has not reached, a day is present only if they had a Math Academy result in Timeback on that America/Chicago day and the nightly had run since, so an absent day is unpulled, never zero; for a backfilled student (`coverage.backfilledAt` set) every day from `backfilledFrom` to the day BEFORE `activityLastDate` is covered and an absent day is a day with no Math Academy task; on `activityLastDate` itself an absent day means "no row yet" (3 to 7 percent of Timeback's rows for a day arrive after the pull, measured on two days; a student whose rows were all late is picked up by the next night's re-pull). `daysRequested[]` says which case applies per day. **Backfill:** a one-off batch begun on 2026-09-17 walks every student who ever held a Math Academy seat in Timeback (matched by the stored id or a one-off lookup) and pulls their whole activity from 2025-07-01 by quarter, bucketed into America/Chicago days by task completion time; it runs in the background over several hours and `GET /store` shows a `backfill` block `{status: "in progress" | "complete", studentsBackfilled, studentsRemaining, updatedAt, finishedAt}` from the batch's first hop on; `studentsBackfilled` counts every student row carrying `backfilledAt` (batch and on-demand alike); a restart of the batch (after a code fix, or to reach students matched since) sets `status` back to "in progress" and removes `finishedAt`. Per student the truth is `coverage.backfilledAt` on the activity response: set means covered; unset means the batch has not reached them and **the first `/activity` read pulls them on the spot** (about five Math Academy calls, `backfilledNow`). So for a covered student a missing day is a day with no Math Academy task. **Failsafe window:** each nightly run covers every day from the day before the last pulled day through yesterday, so a missed night is caught up on the next run and the newest already-pulled day is re-pulled on purpose (late-ingested Timeback rows, late Math Academy tasks); rows are keyed by student, day and task id, so a re-pull overwrites and never duplicates, and the day total is recomputed. A run covers at most fourteen days. `activityLastDate` on `/store` is the newest fully pulled day; `lastActivityRun` says how the last day's pull went (`rePull` true when the run stopped on the overlap day; `daysPulled[]` lists every day the run pulled, oldest first, each with its own `rePull` flag, and `maCallsWholeRun` the run's Math Academy calls; the run of 2026-09-18 carries a list written from its log by the owner, `daysPulledNote` says so). `taskId` matches Timeback's `/tasks/<taskId>/` and lets a reader join the two records; join by id, never by date, because Timeback's `scoreDate` is UTC.
- **`knowledge`** (`…/knowledge`) — Math Academy's knowledge map for the student's current course (or `?courseId=`): response `{ sourcedId, courseId (string), fetchedAt, fromCache, knowledge { courses[], requestedCourse }, note }`; `courses[]` = up to two prerequisite courses **first**, then the course asked for (usually last; match on `id`, a number, or use `requestedCourse {id, name, completion, indexInCourses, topicCount}`, a pointer: the walkable tree is `courses[indexInCourses].units[]`), each `{id, name, completion 0–1, units[] {id, name, stability, modules[] {id, name, stability, topics[] {id, name, stability}}}}`; `stability` 0–1 is Math Academy's estimate of long-term retention per topic, averaged upward; **exactly 0 means Math Academy has no current retention evidence, which covers both untaught topics and topics just failed** (a topic held for three weeks read 0 within hours of a failed review), so zeros with a Timeback task on record belong at the top of a weakest list, not off it (open question #19). Low but non-zero stability on a topic whose only task is a lesson passed in the last day or two is "new, not yet reviewed", not "fading". Non-zero stability on a topic with no task on record exists and is unexplained (open question #21). **copied** on demand: the first ask makes one live Math Academy call; `fetchedAt` dates it; cached for seven days **per course id** (the prerequisite courses are inside the same answer, so asking for them separately costs a second call for the same data); `?refresh=1` forces a new call; a wrong course id is a 404. Roughly two hundred topics per course; the only dataset anywhere that says what the student knows rather than what they did.
- **`mathAcademyState`** — read from Math Academy's own figures **for the current Math Academy course only**: `completed` (`currentCourse.completed` set: Math Academy closed the course, which has been seen at the last lesson and also at 69, 81 and even 0 percent progress with thousands of XP left (a course switch, not a finish), so `completed` alone is not "finished"; report `progress` beside it, open question #24), `at 100, not marked complete` (`progress >= 0.995` and no completion date: Timeback may show a rounded 100), `not started` (`progress == 0` and not completed: nothing done **in this course**; `xpRemaining` is then 0, meaning nothing computed yet, or a per-student figure Math Academy has already sized for them, which is not the course's `totalXp` and varies between students of one course), `in progress` (everything else; also every SAT Math Prep row, where `progress` is null and no state can be read). **A `not started` student can still have Timeback results**: a placement in the new course (progress stays 0 until the first lesson), or lessons and reviews filed under the previous course they were moved from; about one in eight not-started students in a cold run had results. "Never started" is a claim about the results container (zero Math Academy results for the `user.sourcedId`), not about this state. A large share of test accounts sit in `not started`, so use the `nonTest` counts.
- **Range of the store (who has a row):** every student with a current in-window Math Academy seat at `rosterReadAt`, plus students added by a live lookup: asked for by a reader (`live-lookup`), or active on a day the activity pull ran without a stored id (`activity-lookup`, the seatless population of trap 21). Since the backfill of 2026-09-18 every student who ever held a Math Academy seat has a row (`matchedBy: backfill-lookup` for those matched by the batch), so a cohort of finished students who have lost their seat is already in the store (`offRosterSince` set, `courseAgreementAtSnapshot: "no current timeback seat"`; `GET /store/finishers` lists them); only a student never seated since July 2025, and never asked for, reads `not in snapshot` until a reader's first read triggers the lookup.
- **`matchedBy`** — how the Timeback student was tied to a Math Academy record: `known` (the Math Academy id stored on an earlier night was found in tonight's bulk list; the normal case after the first night), `live-lookup` (the student was missing when a reader asked, and one live Math Academy call found them), `activity-lookup` (found by the nightly activity pull for a student with results but no seat), `username` (the Math Academy login on the student's Timeback `userProfiles` equals a bulk-list username; strongest), `email` (the bulk-list username equals the Timeback email), `lookup` (Math Academy answered a per-email lookup; strong), `name` (exactly one bulk-list record with the same first and last name; **low confidence, treat as a hint**). `inSnapshot: false` with `unmatchedReason` = the student was on the Timeback roster at snapshot time and no record matched: `HTTP 404` (no account under this organisation's Math Academy key), `HTTP 401` (an account under another organisation's key), `no email`. `inSnapshot: false` without a reason = not on the Timeback Math Academy roster at snapshot time. (`counts.matchedBy` on `/store` carries every bucket, with `live-lookup`, `activity-lookup` and `backfill-lookup` normally 0: a row added between loads by one of those becomes `known` at the next load.) `backfill-lookup` (the batch backfill found a student who ever held a seat but had no store row, and matched them by one direct Math Academy call; their figures are direct-call figures at `figuresAsOf`).
- **`mathAcademy` fields** (Math Academy's own vocabulary, copied):
  - `id` — Math Academy's student id (a foreign id; the key for the one-off calls in ENABLEMENT § One-off exact figures). `username` — the Math Academy login (PII). `firstName`, `lastName` (PII). `created`, `createdLocal` — account creation (epoch seconds; local string in the student's zone). `deactivated` — Math Academy's account switch; a deactivated account with a Timeback seat is a roster fact to report.
  - `currentCourse.id`, `.name` — **the course Math Academy is actually running the student in.** This is the definitive answer to trap 10: compare it with the Timeback seat (below). Math Academy's course names differ in form from Timeback's titles (`Math Academy - 5th grade` versus `5th Grade Math`, `Prealgebra` versus `Pre Algebra`); `courseAgreement` normalises case, the `Math Academy -` prefix, a trailing `Class` or `Math`, and grade ordinals before comparing. `currentCourse.startDate` — when Math Academy started the student in it.
  - `currentCourse.progress` — 0 to 1, Math Academy's own course completion (Timeback's `pctCompleteApp` is the same quantity as an integer percent at event time). `currentCourse.xpRemaining` — **Math Academy's own XP-left figure**, the one this skill otherwise estimates; where both exist, prefer this and say its date. Math Academy recomputes it on its own schedule, not per task: two consecutive nights showed `progress` moving (0.114 to 0.121 after 82 XP) while `xpRemaining` stayed at 3,063, so two dated figures a day apart can read as "no progress" when there was some; quote it with its date and read `progress` beside it. A 0 while `progress` is below 0.995 (seen on three SAT Math Fundamentals students at 0.97, and on SAT Math Prep) means "unknown, nearly done", not "0 left". `currentCourse.completed` — a date once the course is finished, else null. `currentCourse.grade` (0 to 1) and `letterGrade` — Math Academy's running course grade. `currentCourse.estimatedScore` — on SAT Math Prep, Math Academy reports a predicted SAT score here and `progress` is null; `xpRemaining` is still served there but **is not reliable**: an active student with 149 events read 0 while another read a figure (open question #22). Report the estimated score on that course and treat XP remaining as unknown. `phase` is documented by Math Academy and not served on our key.
  - `schedule` — Math Academy's own daily XP goals per weekday and `paused` (0/1): different from Timeback's enrollment goals. `league` — name, level, position, participants; a gamification signal of low analytic value.
- **Fields readers asked for (2026-09-18).** List rows carry `seatBeginDates[]` (the Timeback seat's `beginDate` per class in this course, for "placed weeks ago"), `currentSeatCount` (distinct Math Academy courses the student currently sits in; 2 or more is invariant 5), `grades[]` (Timeback `users.grades` at roster time; below 4 is a roster fact to question) and, on unmatched rows, `matchedBy: null` and `matchConfidence: null` (nothing was matched). `/store` `counts` carries `studentsWithTwoOrMoreSeats`, `maMatchedToMoreThanOneTimebackStudent` and `sumsNote` (byCourse counts seats, so it sums above the roster by the extra seats). Every timestamp on every route is ISO 8601 in UTC; the offset is written `+00:00` on snapshot-derived fields and `Z` on fields the front writes (`lastTriedAt`, `fetchedAt`, course `windowUtc`), so parse, do not compare strings. `daysRequestedNote` is null whenever `daysRequested[]` is served. `history[]` entries before 2026-09-17T18:00Z carry only `{at, source}`; later ones add `matched` and `roster`.
- **Off-roster rows.** A load replaces the Math Academy figures of every student on the roster; a student who has a row but no current seat at a load (they left the roster, or the row was created by a lookup for a seatless student) keeps their row with the last-known record, `seatsAtSnapshot: []`, `courseAgreementAtSnapshot: "no current timeback seat"` and `offRosterSince` (the first load that found the row without a seat, which is NOT when the seat was deleted: read the seat's `dateLastModified`). They are excluded from every course count and list (no seat), their `hist#` and `act#` rows stay, `backfilledAt` survives, and the per-student route refreshes their Math Academy record by one direct call on read, once per 24 h (`readCalls.maLookupOnMiss`), serving `offRosterSince` and `offRosterNote`. `backfilledAt` and `backfilledFrom` also survive a load for roster students.
- **`courseAgreement`** — computed at read time by one rule: normalise Math Academy's `currentCourse.name` and each live Timeback seat's course name; `agree` if any seat matches, else `disagree`; append `, math academy course completed` when `currentCourse.completed` is set. It is a **name comparison plus a flag**, nothing more: `disagree, math academy course completed` means Math Academy still shows a finished course while Timeback's current seat is a different course. Whether Timeback moved the student before or after the completion, and whether the new seat is the right next course, are not decidable here (open question #7); in cold runs the new seat had been created a month before the completion in one case and a day before it in another. `agree, math academy course completed` = both systems still on the finished course (parked). `disagree` without the flag is the trap-10 case: every Caliper event is being filed under a course Math Academy is not running; the Timeback seat is changed by the school's roster owner and the Math Academy course by a Math Academy admin, and which side is right is not decidable here (open question #7), so report both course names to the platform team. `no current timeback seat` `math academy has no current course`, `no math academy record`, `not in snapshot`. With two current seats the value is `agree` if Math Academy's course matches any of them; all seats are listed. `courseAgreementAtSnapshot` is the same rule (same code path, same vocabulary) against `seatsAtSnapshot`, so a fix made since shows as `disagree` → `agree`; the status route's `counts.courseAgreement` and `byCourse` use this vocabulary too.
- **Range of the store** (what a miss means): the Timeback roster at snapshot time was every active, in-window student enrollment in every section of every course titled `Math Academy…`, sections gathered by `course.sourcedId` as ENABLEMENT B5 does (so a section with an odd title is included); the Math Academy side was every student under this organisation's key. A student not in either at that moment is absent, not negative. The bulk list lags Math Academy's live record by up to a day for progress figures; `lookup`-matched rows were read live at snapshot time.
- **Traps specific to the store:** (a) it is dated; always print `snapshotAt` (or `fetchedAt`, or the task's `date`) next to any figure from it, and read `stale`; (b) a `name` match can be wrong (two children with the same name in different orgs); (c) `mathAcademy.username`, `firstName`, `lastName` are PII under § Students are children; (d) `ma_unmatched` rows (Math Academy students with no Timeback roster match, including deactivated accounts and other campuses) are counted in `/store` and never served row by row; (e) `xpRemaining` can exceed `course.metadata.metrics.totalXp × (1 − progress)` by a wide margin, which is the bias the estimate carries; (f) NIGHTLY activity days are pulled only for students with a Timeback result that day; a BACKFILLED student's rows come straight from Math Academy, so the store can hold tasks Timeback never received (10 store-only tasks in 653 on one cross-check, a per-student Caliper gap), and comparing the two per student is how such gaps are found; (g) the knowledge call is live and counted against Math Academy's fair-use limit: ask for it per student when needed, never loop it over a roster; (h) a `live-lookup` row's `courseAgreementAtSnapshot` was computed at that moment, not at the night's snapshot.

### assessmentResult (Caliper-derived) — one completed Math Academy task

- **one instance:** one task a student completed on Math Academy: a lesson, review, quiz, multistep problem, placement, exam or supplemental task. Genesis of the instance: **copied** (Math Academy emitted the Caliper event; Timeback's bridge adapter wrote the row).
- **id / identity:** `sourcedId` = `caliper_urn:uuid:<event id>`; the same uuid appears as `metadata.caliperSourcedId` and inside `metadata.relatedCaliperEvents[]`. Stable, one per event.
- **finished:** a result is written once, on ingestion, with `scoreStatus` `fully graded`. Nothing updates it. A student redoing a task produces a new event and a new result; `metadata.attempt` counts attempts on the same Math Academy task.
- **native:** list `GET /ims/oneroster/gradebook/v1p2/assessmentResults` with `filter`; instance `GET .../assessmentResults/{sourcedId}`. Filters honoured (probed 2026-09-16/17): `student.sourcedId='…'`, `scoreDate>='<ISO>'`, `scoreDate<='<ISO>'`, `metadata.appName='Math Academy'`, `sourcedId~'caliper_'`, combined with ` AND `; `sort=scoreDate&orderBy=desc|asc`. Filter on `assessmentLineItem.course.sourcedId` is **rejected** (400, "Error in filter query"); to scope by course, list line items by course and join (trap 19). **A student-filtered read returns every app's results**, and rows from other apps may carry no `metadata.appName` at all, so the Math Academy test is `metadata.appName == 'Math Academy'`, never "appName is not some other app" (trap 22).

### assessmentLineItem — the task instance the result grades

- **one instance:** one Math Academy task instance, created alongside the result. **copied.**
- **id / identity:** `sourcedId` = `caliper_` plus a 64-hex digest. One per result in practice.
- **finished:** written once.
- **native:** instance `GET /ims/oneroster/gradebook/v1p2/assessmentLineItems/{sourcedId}`; list `GET .../assessmentLineItems?filter=course.sourcedId='…'` (honoured; paginate at 3000), optionally `AND dateLastModified>='<day>'` to bound it. A list bounded only by `dateLastModified` returns every app's line items and is far too large to page for one day (trap 19); use the per-course filter, or fetch line items one by one for the results you hold.

### enrollment (in a Math Academy class) — the student's seat

- **one instance:** one student in one class section. **captured** by Timeback's rostering (created by the platform's progression or by staff); the Math Academy-derived fields inside `metadata` are **copied** from the latest event that carried them.
- **id / identity:** `sourcedId` (uuid). The EduBridge weekly fact rows reference it as `enrollmentId`.
- **finished:** `status` moves to `tobedeleted`, or `endDate` passes. **Both must be read**, and neither is enough alone: an enrollment can be `active` with an `endDate` in the past, and `tobedeleted` with `endDate` null (trap 2).
- **native:** list `GET /ims/oneroster/rostering/v1p2/enrollments/?filter=class.sourcedId='…'` or `filter=user.sourcedId='…'`; `AND status='active'` is honoured. Every row carries `class {sourcedId, name}` and `course {sourcedId, name}` references (probed both ways 2026-09-17). A student-filtered read returns every app's enrollments; keep the ones whose `course.name` starts with `Math Academy`, or whose `course.sourcedId` is in the course list.

### class and course — the Math Academy container objects

- **one instance:** a class is one section of a course; a course is the catalogue object. Math Academy classes are usually titled `Math Academy - <course> Class`, but not always (sections titled just `Math Academy` exist on the Prealgebra and 5th-grade courses at least), are `metadata.is_automanaged: true` (created by the platform, not by staff), and there are many sections per course, often one per org (trap 1). The course carries `org.sourcedId`. The class's school and the course's org are different objects and need not match. Course ids are the stable key. Titles are not (trap 1).

In the main org: `Math Academy` (bare), `Math Academy - 4th grade`, `5th grade`, `6th grade`, `7th grade`, `Prealgebra`, `Algebra I`, `Geometry`, `Algebra II`, `Precalculus`, `Integrated Math I`, `Integrated Math I (Honors)`, `Integrated Math II (Honors)`, `Integrated Math III (Honors)`, `SAT Math Fundamentals`, `SAT Math Prep`, `AP Calculus AB`, `AP Calculus BC`, `Linear Algebra`. In three other orgs: `Math Academy - 8th grade` (a non-uuid id, no `primaryApp`; students from the main org are seated in it normally, but the topic map covers it thinly, so the Timeback-only heuristic of ENABLEMENT B8 rarely points at it), `Math Academy - Beyond AI` **twice** (two ids, one `active` with `primaryApp` `math_academy`, one `tobedeleted` without it; the only duplicated title), and a partner variant `Nice Academy - Math Academy 6th Grade CCSS Coverage` (`primaryApp` `nice_academy`, `tobedeleted`). ## assessmentResult — field meanings

`sourcedId`, `status`, `dateLastModified`, `student.sourcedId`, `assessmentLineItem.sourcedId` are captured with the row. `scoreDate` and everything in `metadata` is copied from the Caliper event Math Academy sent.

- `score` — percent correct on the task, 0 to 100, higher is better. **copied** (Math Academy's `questionsCorrect / questions`, rounded). `null` where nothing was correct (trap 9). Not the XP.
- `scoreDate` — when the student completed the task, UTC. **copied** (equals Math Academy's task completion time, observed to the second on the build's cross-check). This is the field to sort and window on.
- `dateLastModified` — when Timeback wrote the row. Usually minutes after `scoreDate`, but ingestion can lag by days (invariant 4); never use it as the activity time or as a day boundary.
- `scoreStatus` — always `fully graded` as observed. `inProgress`, `incomplete`, `late`, `missing` are the strings `"false"` as observed (strings, not booleans).
- `metadata.appName` — `Math Academy` for every row this skill is about. **copied** from the sensor mapping. The filter `metadata.appName='Math Academy'` is the estate-wide selector (trap 16). Absent on many other apps' rows (trap 22).
- `metadata.sensor` — `https://mathacademy.com`. **copied.** The Caliper sensor URL.
- `metadata.source` — `caliper`. Rows from other paths (native Timeback quizzes) carry other values and are not Math Academy.
- `metadata.originalObjectId` and `metadata.generatedId` — the Math Academy task URL. **copied.** Two shapes: `https://www.mathacademy.com/tasks/<taskId>/topics/<topicId>/<type>` for `lesson`, `review`, `quiz` and `multistep`, and `https://www.mathacademy.com/tasks/<taskId>/<type>` with **no topic** for `placement`, `exam` and `supplemental`. A handful of rows match neither shape (3 of 47,020 since 1 August: two Timeback-hosted `…/courses/<id>/activities/<slug>` URLs and one `…/tasks/aj-flow/<date>/manual`): give your parser an "other" bucket, count it, and treat those rows like trap 27's adjustments (not tasks). Three facts ride inside it and nowhere else as fields:
  - `<taskId>` — Math Academy's task id, a foreign id (a claim; matching to Math Academy is the caller's).
  - `<topicId>` — Math Academy's topic id on **lesson and review** tasks, a foreign id; it joins to the knowledge map's `topics[].id`. The same topic id recurs across students and across courses (trap 8). **On `quiz` tasks the slot holds a quiz-instance id and on `multistep` tasks a multistep-problem id, neither a topic id** (trap 25): a cold run found none of a student's multistep slot ids in any of the three courses of their knowledge map.
  - `<type>` — the task type. Allowable values observed: `lesson`, `review`, `quiz`, `multistep`, `placement`, `exam`, `supplemental`. Two further URL shapes carry `appName` Math Academy but are **not tasks** (trap 27): `…/manual-xp-assignment/urn:uuid:…` (sensor `https://timeback.timeback.com/manual-xp-assignment`, title "Manual XP Assignment - Math") and `…/tasks/<id>/<date>/correction-rerun` (title "Data Correction", several rows sharing one task id); both carry `score` null and no `totalQuestions`/`correctQuestions`; keep them out of every task, failure and minutes count and report their XP as adjustments. `lesson` is new material in the current course; `review` is spaced repetition and routinely revisits earlier courses' topics; `quiz` and `multistep` follow lessons; `placement` is the entry diagnostic; `exam` and `supplemental` are rare. Observed set, not enforced.
- `metadata.xp` — XP **awarded** for the task, an integer, **signed**: it equals Math Academy's `xpAwarded` (the store's `tasks[].xpAwarded`), not the task's nominal `xp` value. **The sign carries two different meanings.** Negative XP is Math Academy's penalty for rushing and guessing (clicking through the instruction, answering fast and wrong), a habit signal. Zero XP is a failed task with no penalty, a difficulty signal. Keep them apart in every count (§ Derived quantities). Observed: zero on tasks with 2 of 5 or 3 of 6 correct; −1 on a lesson at 6 of 9; positive XP with `masteredUnits` 1 on quizzes and multisteps at 43 to 58 percent. Math Academy's exact award rules per task type are not published (open question, ticket 20), so the sign of the awarded XP is the reader's only Timeback-side verdict. Higher is better; Math Academy calibrates 1 XP to about one minute of focused work. The same number appears as `xpEarned` on the EduBridge ActivityEvent row.
- `metadata.totalQuestions`, `metadata.correctQuestions` — question counts on the task. **copied.** Both present on every Math Academy TASK row observed (absent on the two non-task shapes of trap 27); `correctQuestions` is 0 on null-score task rows (trap 9). It is the EduBridge weekly fact rows that carry `correctQuestions: null`.
- `metadata.masteredUnits` — Math Academy's count of units the task advanced. **copied.** 0 or 1 on nearly every row; meaning of larger values truly unknown.
- `metadata.attempt` — attempt number on this Math Academy task. **copied.** 1 on nearly every row.
- `metadata.pctCompleteApp` — the student's completion percent of their **Math Academy course** at the moment of this event, as a **string** of an integer 0 to 100. **copied.** Higher is further through the course. Equals Math Academy's own progress figure rounded to a whole percent (invariant 2; whether it rounds or truncates is not stated, so **"100" can be Math Academy's 0.995**: one student read 100 here with 9 XP left and no completion on Math Academy). Absent on some rows, most often lessons: between 3 and 30 percent of a student's rows across the students checked, in one case a whole evening session; measure with the query in trap 3. **This, on the student's newest result filed under the seat's course, is the reliable Timeback-side place to read progress**; the enrollment's copy is often missing (trap 3), and the store's `progress` (0 to 1, dated) is exact.
- `metadata.lessonType` — `external-lesson` for every Math Academy row. Structural marker that the content lives outside Timeback.
- `metadata.subject` — `Math`.
- `metadata.studentEmail` — **not on Math Academy rows**, but present on many other apps' Caliper rows that a student-filtered read returns (PII; trap 24).

## assessmentLineItem — field meanings

- `title`, `description` — the Math Academy topic name on lesson and review items, `Quiz N` on quizzes, and **the raw task URL** on placements (observed; exams and supplementals presumably alike). **copied.** Human label; the topic id in the URL is the key.
- `course.sourcedId` — the Timeback course this task was **filed under**: the enrollment the platform matched at ingestion, which may since have been deleted (load-bearing rule 2; traps 10, 21).
- `metadata.externalUrl` — the same task URL as the result's `originalObjectId`.
- `metadata.courseId` — duplicate of `course.sourcedId`.
- `resultValueMin` / `resultValueMax` — 0 / 100.

## enrollment — field meanings

- `status` — `active` or `tobedeleted`. `active` alone does not mean current (trap 2).
- `beginDate`, `endDate` — the seat's window; `endDate` is **absent from the row** when the seat is open (not present as null: a reader testing `endDate is null` on a missing key crashes or misreads), or in the past while `status` is still `active`; a `tobedeleted` seat usually carries no `endDate` either, so deleted seats span forever on paper and overlap the seats that followed them; the closest served proxy for when a seat was closed is its `dateLastModified`.
- `primary` — the string `"true"` or `"false"`. **Not a reliable selector for the student's main Math Academy course**: in some courses every Math Academy enrollment is `"false"`, in others one is `"true"`. Prefer the current in-window Math Academy enrollment with the latest `beginDate`; where two are current, report both (invariant 5).
- `metadata.pctCompleteApp` — the latest course completion percent, an **integer** here (a string on the result). **copied** from the latest event that carried one. **Often absent**, including on seats that are months old with hundreds of results, and absent on most `tobedeleted` seats even when the results under them reached 100 (trap 3). Read progress from the newest result instead and treat this field as a convenience.
- `metadata.pctCompleteAppUpdatedAt` — when that percent was last written, UTC. The staleness clock for the percent, where present.
- `metadata.metrics.totalXp`, `totalLessons`, `totalGrades` — **not the student's running totals.** On many seats `totalXp` equals the course's own `metrics.totalXp` at the time the seat was created (a size snapshot); on others it is a different figure that does not equal the XP the student earned under the seat either. Genesis: **truly unknown**; treat as unusable. The student's XP under a seat is the signed sum of `metadata.xp` over that seat's results (ENABLEMENT A9).
- `metadata.goals.dailyXp`, `dailyLessons`, `dailyActiveMinutes`, `dailyAccuracy`, `dailyMasteredUnits` — Timeback's daily targets for the enrollment. **judged** (platform defaults, overridable by staff). These are Timeback's goals, not Math Academy's schedule.
- `metadata.completionType`, `completionReason` — present on enrollments a person closed manually; free text.
- `user.name` — the student's display name on every enrollment row (PII; trap 24).

## course — field meanings

- `title` — see the domain above. Not canonical: one title (`Math Academy - Beyond AI`) names two course ids, one course is titled just `Math Academy`, and class titles derived from course titles vary in case (trap 1).
- `grades[]` — the grade band the course is intended for.
- `metadata.primaryApp` — `math_academy` on most rows; absent on `Math Academy - 8th grade` (another org, non-uuid id) and on the `tobedeleted` `Beyond AI` row; `nice_academy` on the partner variant. Not a reliable selector for "is this a Math Academy course"; use the title filter plus the id list.
- `metadata.metrics.totalXp` — the course's size in XP, set by the school from Math Academy's published XP-with-reviews figure for that course. **judged** (by the school, per course). The denominator for the XP-remaining estimate; it can lag a Math Academy re-size (trap 11). Absent on the bare `Math Academy` course and the `Beyond AI` courses, which hold no real students by rule.
- `metadata.contactEmail` — a staff contact on some course objects (PII; trap 24).

## EduBridge — field meanings

- `activityMetrics.xpEarned`, `totalQuestions`, `correctQuestions`, `masteredUnits` — sums over the day (daily activity) or the single event (weekly fact). **computed** from the copied result rows.
- `timeSpentMetrics.activeSeconds`, `inactiveSeconds`, `wasteSeconds` — seconds. **`activeSeconds` for Math Academy is Math Academy's `timeEngaged` clock**, the part of the task Math Academy judged the student attentive, not wall time: on every task that had a time row, across four cold runs (samples of 73, 10, 6 and 6 tasks), it equalled the store's `timeEngagedMs` on 301 of 304 pairs (the other three 2 seconds apart) and was below `timeElapsedMs` wherever the two differ (elapsed has run to 2.9× engaged). So Timeback's "active minutes" already exclude idle wall time, and the elapsed-versus-engaged gap is visible only in the store; the productive clock reaches neither Timeback container. **A day's Timeback minutes are a floor that can be half the truth**: tasks without a time row (invariant 1; a fifth of one student's tasks) are absent from the day cell too, and the missing rows skew long (one day: 36 Timeback minutes against 65 engaged minutes in the store, the four missing tasks being the four longest). Count the tasks without a time row beside any minutes you report. `inactiveSeconds` and `wasteSeconds` are **always 0 for Math Academy** (trap 4): Math Academy sends no waste signal; zero means unmeasured, never clean.
- `apps[]` — the apps contributing to the cell; `Math Academy` is the label.
- weekly fact rows — `eventType` is `ActivityEvent` or `TimeSpentEvent`; `datetime` is the event time (UTC) and the field to join on (or `source`, the Caliper event id, which is the collision-free key); `date` is the local day in the zone passed; `userId` = `user.sourcedId` (the key the PII rule wants); `courseId`, `courseName`, `enrollmentId` name the filed course and seat; `activeSeconds` arrives as a **string** with two decimals (engaged time, see above); `activityId` is the Math Academy topic URL on TimeSpentEvent rows (no type segment) and null on ActivityEvent rows; `activityName` is the topic title on ActivityEvent rows, and on TimeSpentEvent rows it is the topic title on recent rows but the **course title** on rows generated before mid-September 2026 (trap 26). `email` is on every row (trap 24).

## Derived quantities this skill teaches (never fields on the wire)

- **Estimated XP remaining in the current course.** Math Academy does not send its XP-remaining figure to Timeback; the snapshot store carries it exactly, dated. Every input for the estimate is on the wire: `remaining ≈ course.metadata.metrics.totalXp × (1 − pct / 100)`, where `pct` is the newest result's `pctCompleteApp` **whose line item is filed under the seat's course** (check the line item; a percent filed under another course means no estimate and a flagged seat, ENABLEMENT B4), falling back to the enrollment's copy only when no such result exists, basis "timeback course XP". **computed** by the reader from two copied inputs. The rule order, including the no-estimate cases, is in `reference/course-xp-size.json`: no `totalXp` on the course (the bare `Math Academy` and `Beyond AI` courses, where no real student belongs); no percent anywhere yet; SAT Math Prep (Math Academy reports an estimated SAT score there instead of progress, a figure Timeback never receives; SAT Math Fundamentals still reports progress and is estimated normally). **Accuracy:** poor, and the sign is not guaranteed. Against Math Academy's exact figure (denominator: the exact figure; this one statement is the current band and every other mention points here) the estimate ran from **64 percent too high to 67 percent too low** across about thirty students checked on 2026-09-17 (the high side near the end of a course, where a rounded percent against a small remainder swings wildly; median about a quarter low), usually low (median about a third low) because Math Academy awards extra XP on failed reviews and retries beyond the course's nominal size. It is a Timeback-only fallback for "a lot left / a little left / nearly done", never a number to publish. **The exact figure is in this skill's store**, dated (`…/store/student/{sourcedId}`, `mathAcademy.currentCourse.xpRemaining`), including on SAT Math Prep; read it first.
- **Minutes to earn 1 XP** (the pace measure). Math Academy calibrates 1 XP to one minute of fully focused work for a serious but imperfect student (its own published design), so `engaged minutes in the window ÷ XP awarded in the window` reads directly: **0.9 to 1.1 is the good zone for lesson-heavy work** (the calibration is for new material; reviews, quizzes and exams pay XP in far less time, so a review-heavy week reads 0.2 to 0.4 with clean habits: report the task mix beside the pace, and judge "racing" by the negative-XP share, not by a low pace alone); well above 1.1 is unfocused or struggling; well below 0.9 is racing through, or material that is too easy. **computed** by the reader from two copied inputs. Rules: use a week or more (one bad day can make net XP zero or negative and the ratio meaningless); when XP awarded over the window is **below 20**, report "no pace: too little XP earned" instead of a number (a student who earned 6 XP in 449 engaged minutes reads 75 minutes per XP, which is not a pace but a habits problem; the negative-XP share beside it says so); take engaged minutes from the store's `timeEngagedMs` where the day is pulled, else from Timeback's time rows and say the count of tasks without one (they are a floor); name the window and the clock. Denominator: XP awarded, signed, over the same tasks whose minutes you summed.
- **Share of lessons with negative XP** (the habits measure). Math Academy awards negative XP as a penalty for rushing and guessing (clicking through instruction, answering fast and wrong); it is a behaviour signal, not a difficulty signal. `lessons with metadata.xp < 0 ÷ lessons in the window`, lessons only (URL type `lesson`; reviews carry most negative XP and would double the share), labelled "of lessons". Report beside the next one, never merged with it.
- **Share of lessons with zero XP** (the difficulty measure). Zero XP is a failed lesson with no penalty: the student worked at it and did not get it. `lessons with metadata.xp = 0 ÷ lessons in the window`. A high zero share with a low negative share is a teaching gap; the reverse is a habit to coach. Math Academy's exact award rules are not published (open question, ticket 20), so both shares are read from the sign of the awarded XP, which is Math Academy's own verdict.
- **Suspect-course flag.** Whether the lessons a student is being taught point at a course other than the one they are enrolled in, inferred from topic ids (ENABLEMENT B8; the store's `courseAgreement`, A7, is the answer). A heuristic with a stated false-alarm profile (trap 8), never a verdict.
- **Student timeline.** A student's Math Academy seats over time, with the events filed under each, the percent reached, and the gaps (ENABLEMENT A9 for Math Academy's episodes, B9 for the Timeback-filed half). Assembled from all-time results plus line items plus enrollments; nothing on the wire serves it as one object.

## Expected invariants

1. **One result, one line item, one ActivityEvent row per Math Academy event; a TimeSpentEvent row for most but not all.** Standing: **observed-empirically**. Results, line items and ActivityEvent rows matched one-to-one on every cold run; TimeSpentEvent rows were fewer, so **active minutes summed from weekly facts are a floor**. Test: for one student and one window, count results with `metadata.appName='Math Academy'`, count weekly fact rows with `app = "Math Academy"` grouped by `eventType`; expect results = ActivityEvent rows ≥ TimeSpentEvent rows.
2. **`pctCompleteApp` equals Math Academy's own course progress.** Standing: **observed-empirically** during the build across the active population (agreement within a point or two for the large majority). Not testable from Timeback alone. It is **not** monotonic: within one enrollment the percent can step down a point and back up (observed on two cold runs), so a decrease is not proof of a course change.
3. **Daily `xpEarned`, questions, correct and mastered units for Math Academy equal the sums over that student's Math Academy results that day.** Standing: **observed-empirically**, exact on every day checked across four cold runs. Test: sum results by day (in the same timezone passed to EduBridge) and compare with `factsByApp[<day>].Math["Math Academy"].activityMetrics`.
4. **`scoreDate` is the task completion time; `dateLastModified` is ingestion time.** Standing: **observed-empirically**. Ingestion is usually minutes later but has been observed a week later, so never window on `dateLastModified`.
5. **A student holds at most one current Math Academy enrollment per course.** Standing: **expected-but-violated**. Some students hold two current in-window Math Academy enrollments in different courses; a grade course beside an SAT course is legitimate, two grade courses is not. Query: enrollments filtered by `user.sourcedId`, keep `status='active'`, course title starting `Math Academy`, today inside `beginDate..endDate`; report students with more than one, naming both courses. Do not weaken the definition; report the rows.
6. **`score` = round-half-up(100 × `correctQuestions` / `totalQuestions`), with `null` where `correctQuestions` is 0.** Standing: **observed-empirically** on every row checked (5 of 8 = 62.5 is served as 63; a banker's-rounding check flags a false violation).

## Known traps

Each carries the query that measures its blast radius today; no figure of this document's travels with it.

1. **Class and course titles are not canonical, and one title names many classes.** One course title, `Math Academy - Beyond AI`, names two course ids; one course is titled just `Math Academy`; the `8th grade` course lives in a different org under a non-uuid id; a partner org carries a `Nice Academy - Math Academy …` variant; class titles, built from course titles, appear with differing case for the same grade; and **a course has many class sections with the identical title**, typically one per org, several with no active enrollment. "The Algebra II class" is a set of classes on one course id, not one class. Use `course.sourcedId`, and gather every section with `classes/?filter=course.sourcedId='…'`. Measure: `GET .../courses/?filter=title~'Math Academy'&limit=100`, group by title, count titles with more than one id; `GET .../classes/?filter=title~'Math Academy'&limit=3000`, group by `course.sourcedId`, count classes per course.
2. **An `active` enrollment can be over, and a deleted one can look open.** `status='active'` with `endDate` in the past is common; `status='tobedeleted'` with `endDate` null is common too. Current means `status='active'` AND today within `beginDate..endDate` (null `endDate` = open); a `tobedeleted` seat is never current whatever its dates. Measure: list a class's enrollments, count `active` rows whose `endDate` < today, and `tobedeleted` rows whose `endDate` is null.
3. **The enrollment's `pctCompleteApp` is often missing, it stalls, and "100" is not "finished".** It appears only after a percent-bearing event has arrived for that seat, a sizeable minority of results carry no percent (lessons most often; whole evening sessions for some students), and it is absent on most deleted seats and on many active seats that have months of results. "Who finished" cannot be read from enrollments, and not safely from results either: the percent is a rounded integer (a Timeback "100" has been Math Academy's 0.995), it can step back to 99, and Math Academy marks the course `completed` only at the student's last lesson, five months after Timeback's first 100 in one case. ENABLEMENT A5 lists finishers by Math Academy's own `completed` flag (`/store/finishers`) and B6 reads Timeback's rounded 100 for the ones Math Academy has already re-seated. Absence never means "never active": the same student may have hundreds of results under other seats. Measure: enrollments in Math Academy classes with `status='active'` and no `metadata.pctCompleteApp`, over all such enrollments; results in a window without `metadata.pctCompleteApp`, over all rows.
4. **Waste is always zero for Math Academy.** `wasteSeconds` and `inactiveSeconds` are 0 on every Math Academy cell because the app sends no such signal. A dashboard that reads zero waste as good behaviour is wrong. Measure: weekly facts for any Math Academy student, count rows with `wasteSeconds != "0.00"`.
5. **Up to two fact rows per task.** Summing weekly facts without filtering `eventType` double counts events and mixes XP rows with time rows. XP and questions are on `ActivityEvent` rows; seconds on `TimeSpentEvent` rows; `correctQuestions` may be null on ActivityEvent rows. Some tasks have no time row at all (invariant 1). Measure: for one student-week, count rows by `eventType` against results.
6. **Duplicate time rows are reported upstream.** The timeback_production skill reports literal duplicate TimeSpentEvent rows in the processed-facts store for some students. None were found on the weekly facts route in three cold runs; dedupe on (`datetime`, `activityName`, `activeSeconds`) anyway before summing time. Measure: weekly facts, count exact-duplicate TimeSpentEvent rows.
7. **The task type is inside the URL, and three types have no topic.** Nothing else on the row says lesson vs review. Parse the last path segment; `placement`, `exam` and `supplemental` URLs have no `/topics/<id>/` segment. Measure: count results whose `originalObjectId` matches neither URL shape.
8. **Reviews revisit earlier courses, quizzes and multisteps carry no topic id, and adjacent courses share topics.** Inferring a student's course from topic ids works only on `lesson` events (trap 25), and even then adjacent grade-level courses share many topics, so a student in a grade N class doing grade N−1 lesson topics is common and usually legitimate. Any topic-to-course map is a majority label, not Math Academy's catalogue, and **its range is the courses with enough lesson events in the window**: a thinly covered course (8th grade, the high-school courses) is rarely pointed at, so its students read uncheckable or get the neighbouring grade. It is dense for grade-level courses and thin for high-school courses. Against the store's definitive check on two grade courses the heuristic scored precision about one in eight and recall about one in five: use it only where the store is stale or silent (ENABLEMENT B8). Measure: build the map as example 7 step A says and report topics mapped, topics dropped by the share bar, and topics with too few students; per cohort, count students with fewer than three mapped lesson topics.
9. **A null `score` is a task with zero correct answers.** On every cold run, every null-score Math Academy result carried `correctQuestions` 0 and `xp` at or below 0. Read `score: null` as 0 percent. Whether any other cause produces a null score is open (question #9). Measure: results with `metadata.appName='Math Academy'` in a window, count `score` null, and within those count `correctQuestions` not equal to 0.
10. **The filed course is a Timeback enrollment's course, not Math Academy's.** If Timeback enrolled a student in one course while Math Academy runs them in another, every event is filed under Timeback's course, `pctCompleteApp` reports progress in Math Academy's course, and the line item cannot reveal the difference. Detecting it from Timeback alone is heuristic (ENABLEMENT B8); the definitive check is the store's `courseAgreement` (ENABLEMENT A7), which compares Math Academy's own course with the live seat. There is **no reliable Timeback-side tell** for "finished on Math Academy but not moved": the "reviews only after 100" idea failed on every actionable case in a cold run (all had lessons after the 100). Math Academy marks a course `completed` at the student's last lesson, which can be months after Timeback first shows 100 (trap 3, ENABLEMENT A5). Measure: the store's `byCourse` counts of `disagree` values; the heuristic's flags against them.
11. **A course's `totalXp` can lag Math Academy's XP-with-reviews figure.** The school sets `course.metadata.metrics.totalXp` by hand from Math Academy's published per-course XP; on 2026-09-17 every course carrying a figure was checked against the school's table and matched after a correction that day. When it lags, XP-remaining estimates on that course read low. Standing: **observed-empirically**. Measure: for one course, compare `course.metadata.metrics.totalXp` with the median over its students who began the seat near the course start of `(signed sum of result xp under the seat) ÷ (newest pctCompleteApp / 100)`. Never use `totalXp` as a denominator for progress; progress is `pctCompleteApp`.
12. **Test, shadow and demo accounts fill rosters, and some courses hold only them.** `users.metadata.isTestUser` marks some; **others carry no flag at all** (a section had 10 of 16 unflagged seats following a `Grade5 ShadowNN` naming pattern, with full Math Academy records), and a reader must not inspect names to find them. So the store judges it server-side: `isLikelyTest` on every store row and list row = the flag, OR a synthetic naming pattern (shadow, test, demo, e2e, mock, "Guide Sixth Grade"), OR a test campus (100for100, Guide School, Mock, LwAI); the store's `nonTest` counts use it. Use `isLikelyTest`, never names. **The flag is not filterable on the users list** (`users/?filter=metadata.isTestUser='true'` answers 200 with zero rows; unquoted, 422), so it is read per user (`users/{id}`), per class (`classes/{id}/students`), or from the store's course student list, which carries it per row. A cold run spent three quarters of an estate-wide day's calls on this; take the flag from the store list where the student has a seat and only fall back to `users/{id}` for the rest. They are a large share of enrolled Math Academy students and a negligible share of daily activity, so any roster census includes them unless filtered and any activity census barely does. The bare `Math Academy` course and the `Beyond AI` courses hold no real student by rule `[owner, 2026-09-17]`; on that date every active enrollment in them was a flagged test user, and a non-test enrollment there is a roster defect. Measure: for a cohort, count `metadata.isTestUser = true` over roster students and over students with a result in the window; for the three courses named, active in-window enrollments whose user is not a test user (expected: none).
13. **The Timeback grade is not the Math Academy course.** `users.grades[]` is the student's enrolment grade; Math Academy places students by placement test, often one or more courses above or below. Never infer course from grade or grade from course.
14. **`search=` works on courses and is ignored on classes.** On `courses/` it filters by title; on `classes/` it returns the whole collection with a normal 200 (probed 2026-09-17). Use `filter=title~'…'` or `filter=course.sourcedId='…'` on classes. Measure: compare `totalCount` with and without `search` on each route.
15. **`/classes/{id}/students` returns `users`.** The array key is `users`, not `students`; a reader keyed on the documented name gets an empty list and a clean 200.
16. **The estate-wide selector is undocumented.** `filter=metadata.appName='Math Academy'` works today and is the only way to read all Math Academy events without a student list. It is not in the OpenAPI filter list; re-check it before relying on it. Measure: the call with `limit=1`, expect `totalCount` > 0.
17. **Timezone decides the day, and nothing served tells you the student's.** EduBridge daily cells move with the `timezone` parameter; OneRoster `scoreDate` is UTC. No served field carries a student's or campus's timezone. Use the school's local zone if you know it, otherwise UTC on both sides, and say which you used. Weekly facts return Sunday to Saturday in the zone passed.
18. **Pages cap at 3000 and `totalCount` is the truth.** Loop on `offset` until `offset >= totalCount`; a short page mid-way is not the end. A suspiciously round `totalCount` is still the count; confirm by splitting the window in two and adding. **Ingestion continues while you page**: `totalCount` grew during a 19-page read, so always pass `sort=scoreDate&orderBy=asc` on a paged results read, or rows shift across page boundaries and are missed or doubled.
19. **Scoping results by course is rejected, and scoping line items by date alone is too big.** `assessmentLineItem.course.sourcedId` in a results filter returns 400. Line items filtered only by `dateLastModified` return every app's items for the day, hundreds of pages. Scope line items by `course.sourcedId` (optionally `AND dateLastModified>=`), or fetch line items one by one for the results you hold. Measure: `assessmentLineItems?filter=dateLastModified>='<day>'&limit=1`, read `totalCount`.
20. **`/classes/{id}/students` over-reports the roster.** It returns every user who has ever held an enrollment in the class, including users whose only enrollment is `tobedeleted`; a section with zero active enrollments still returns users. Take the roster from enrollments (`status='active'`, today in the date window) and use the students route only to resolve those ids to `metadata.isTestUser`. Measure: for one class, users from the students route against active in-window enrollments.
21. **Events are filed under the enrollment matched at ingestion, which is often a deleted one, and sometimes none current at all.** The line item's course is that enrollment's course; when a student is moved, older events stay under the old course and new ones can keep landing there; some active students have no current Math Academy enrollment and every event of theirs is under a deleted seat. Joining events to the student's current enrollment mis-attributes or drops them. Measure: for one UTC day of Math Academy results, count rows whose line item course differs from the student's current in-window Math Academy enrollment course, and rows whose student has no current one.
22. **A student-filtered results read is multi-app, and other apps' rows may lack `appName`.** Test `metadata.appName == 'Math Academy'` exactly; combine `student.sourcedId` with `metadata.appName` in the filter to avoid paging other apps' rows. Measure: results for one student, count rows by `metadata.appName` including absent.
23. **The daily `Math` cell mixes apps.** `facts[<day>].Math` sums Math Academy with any other math app the student used that day (Math Raiders is the usual co-occupant). Read `factsByApp[<day>].Math["Math Academy"]`. Measure: for one student-day, compare `facts[<day>].Math.activityMetrics.xpEarned` with the Math Academy cell in `factsByApp`.
24. **Person-bearing values arrive unasked.** Every enrollment row carries `user.name`; every weekly fact row carries `email`; other apps' result rows carry `metadata.studentEmail`; course objects carry `metadata.contactEmail`; the class students route returns full user records. A reader that caches raw responses has PII on disk. See § Students are children.
25. **Quiz and multistep URLs carry an instance id in the topic slot.** `/topics/<id>/quiz` ids are per quiz instance and `/topics/<id>/multistep` ids are per multistep problem, not topic ids: neither joins to the knowledge map, and grouping "by topic" over them fragments them while voting on them poisons a topic map. Group quizzes and multisteps separately by line-item title; only `lesson` and `review` slots are topic ids. Measure: for one student, count distinct quiz and multistep slot ids found in their knowledge map's `topics[].id` (expected: none or a numeric coincidence; 3 of 80 coincided for one student) against lesson ids found (expected: all).
26. **The weekly TimeSpentEvent `activityName` changed meaning in mid-September 2026.** On older rows it is the **course** title; on recent rows it is the topic title. Join time rows to results on `datetime` (equal to `scoreDate`), never on the name. The fact shape has drifted once; expect it to drift again. Measure: for one student, count TimeSpentEvent rows whose `activityName` starts with `Math Academy -`.
27. **Not every `appName` Math Academy row is a task.** Timeback's own XP bookkeeping (manual XP assignments, data-correction re-runs) is stamped `appName` Math Academy; the tell is `metadata.sensor` (`https://mathacademy.com` on tasks) and the URL shape (trap 7). Measure: for one student, count rows whose sensor is not `https://mathacademy.com` or whose URL is neither task shape (expected: a handful; report their XP as adjustments).

## Relationships

- `assessmentResult.assessmentLineItem.sourcedId` → `assessmentLineItem.sourcedId`; `assessmentLineItem.course.sourcedId` → `course.sourcedId`. **This is the only truthful path from an event to the course it was filed under** (trap 21).
- `assessmentResult.student.sourcedId` → `user.sourcedId` → `enrollment.user.sourcedId`; `enrollment.class.sourcedId` → `class.sourcedId` → `class.course.sourcedId`; `enrollment.course.sourcedId` is also present directly on the enrollment row.
- EduBridge weekly fact `enrollmentId` → `enrollment.sourcedId`; fact `source` → the result's `sourcedId` (ActivityEvent) or the Caliper event id (TimeSpentEvent); fact `courseId` → `course.sourcedId`; fact `datetime` = result `scoreDate`.
- Foreign ids held here as claims: the Math Academy task id and topic id inside the task URL, and the Math Academy login username on `userProfiles`. Matching any of them to Math Academy's own records is the caller's, across both systems' contracts. This skill builds no crosswalk to Math Academy.

## Students are children — what a reader may publish

Every student-level row this source serves is about a minor. The identifiers on the wire (`user.sourcedId`, `email`, `givenName`/`familyName`, `identifier` (SIS number), the Math Academy login username on `userProfiles`, `enrollment.user.name`, weekly-fact `email`, other apps' `metadata.studentEmail`) are **person-bearing fields, marked here as PII**, and several arrive whether asked for or not (trap 24). A reader may use them inside its own session to join and to answer the question it was asked. A reader **publishes none of them**: anything that leaves the session (a report, a dashboard, a ticket, a message to a third party, a file another process will read) carries counts, classes, course ids, aggregates, or opaque `user.sourcedId` values the recipient is entitled to resolve, and never a child's name, email, SIS number or login, and never a row that identifies one child on its face. A one-row-per-student output keyed on `user.sourcedId` is allowed inside the session and for a recipient entitled to resolve those ids (a guide, a dashboard behind the school's login); it is not a public artifact. If you cache raw responses, scrub the fields above first, **by path, not by key name**: `name` on knowledge-map courses, units, modules and topics, `courseName`, `topicName` and the titles in `/store/courses` are curriculum, not a child, and deleting them costs you the answer (a cold reader lost three unit names that way). One more source of names: Timeback course and class titles built for one student carry a **person's name**, and it can be the child's ("<Name>'s Custom … Skill Plan", "<Subject> Hole-Filling - <Name>", "<Name> – <exam> MCQ Practice" were all seen on one student's seats on 2026-09-18). Rule: the only course titles a reader may quote are the `Math Academy - …` titles in `reference/timeback-math-academy-courses.json`; every other course or class title on an enrollment row is treated as person-bearing and described by kind ("a hole-filling course", "a custom skill plan", "a Math Raiders course"), never quoted. The worked examples key their outputs on `user.sourcedId`, and resolve an email to an id once, at the start, where a person hands you an email. This is stated by this skill's front under `pii` and binds every surface built on this source.
